# TTL 기반 임시 인증번호 (해싱 key + SET TTL)

Redis의 만료(TTL) 기능을 활용해, 문자로 발송하는 인증번호처럼 한정된 시간 동안만 유효한 데이터를 별도의 정리 배치 없이 관리하는 패턴이다.

## 개념

- 인증번호는 발급 후 일정 시간이 지나면 자동으로 무효화되어야 한다. Redis `SET key value EX seconds`로 저장하면, TTL이 지난 뒤 Redis가 알아서 키를 삭제해준다 (별도의 만료 배치/스케줄러 불필요)
- 전화번호 같은 개인정보(PII)는 그대로 key로 쓰지 않고, 해싱한 값을 key로 사용한다. Redis 서버가 노출되더라도 key만으로 실제 전화번호를 알 수 없게 하기 위함이다.
- 인증 성공 여부와 무관하게 조회 즉시 삭제하는 대신, **입력값이 일치할 때만** 삭제한다. 사용자가 인증번호를 잘못 입력한 경우에도 같은 코드로 재시도할 수 있어야 하기 때문이다.

## 동작 흐름

### 인증번호 발송 (Write)
1. 6자리 난수 인증번호를 생성한다.
2. 전화번호를 SHA-256으로 해싱해 key를 만든다.
3. `SET key code EX 300` - 인증번호를 TTL 300초로 저장한다.
4. 실제로는 이 시점에 SMS를 발송한다고 가정한다. (예제에서는 로그로 대체)

### 인증번호 검증 (Read + Conditional Delete)
1. 동일하게 전화번호를 해싱해 key를 만들고 `GET`으로 저장된 인증번호를 조회한다.
2. 값이 없으면(만료됐거나 발급된 적 없음) 400 에러를 반환한다.
3. 입력값과 저장된 값이 다르면 400 에러를 반환한다. **이때 키는 삭제하지 않는다.** 오타를 낸 사용자가 같은 인증번호로 다시 시도할 수 있어야 하기 때문이다.
4. 값이 일치하면 인증 성공 처리 후 `DELETE`로 즉시 키를 삭제한다. 한 번 사용한 인증번호가 재사용되는 것을 막기 위함이다.

## 이 패턴의 장점

- 만료 배치 불필요: 인증번호처럼 유효기간이 있는 데이터를 RDB에 저장하면 만료 여부를 애플리케이션이 직접 체크하거나 배치로 정리해야 한다. Redis TTL은 이 만료 처리를 Redis에 위임해 별도 배치 자체를 없앤다.
- 불필요한 디스크 I/O 방지: RDB 배치는 결국 어차피 삭제될 데이터를 위해 주기적으로 테이블을 스캔하고 `DELETE` 쿼리를 실행하는 것이라, 불필요한 디스크 I/O와 DB 부하를 유발한다. TTL은 이런 낭비 자체가 없다.
- 개인정보 보호: 해싱된 key를 사용해 Redis 서버가 노출되더라도 key만으로 실제 전화번호를 알 수 없다.

## 이 예제의 구조

```
authcode
├── controller/AuthCodeController.java   # 인증번호 발송 + 검증
└── dto/
    ├── SendCodeRequest.java             # 발송 요청 
    ├── SendCodeResponse.java            # 발송 응답 
    ├── VerifyCodeRequest.java           # 검증 요청 
    └── VerifyCodeResponse.java          # 검증 응답
```

- `POST /auth/send` → `SET` (TTL 300초)
- `POST /auth/verify` → `GET` → 비교 → (일치 시에만) `DELETE`
